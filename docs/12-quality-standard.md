# 駅ページの品質基準

**方針: まず日本語で作り切る。多言語展開はそのあと。**

理由は単純で、既存の不動産まとめ記事に対する優位は「深さ」でしか作れないから。
浅い記事を13言語に翻訳しても、浅い記事が13個になるだけで勝ち筋にならない。
逆に、深い日本語ができていれば、それを各言語にローカライズしたものは
その言語圏に存在しない品質のコンテンツになる。

---

## 1. 既存コンテンツの何が足りないのか

不動産ポータルの街紹介やまとめブログを、実際に住む場所を探す目線で読むと、
判断に必要なことがほとんど書かれていない。

| よくある記述 | 何が問題か |
|---|---|
| 「駅前にスーパーがあり便利です」 | どのスーパーか。価格帯は。徒歩何分か。閉店は何時か |
| 「治安が良く落ち着いた街です」 | 何を根拠に。夜の人通りは。帰り道は暗いか |
| 「都心へのアクセス良好」 | どこへ何分か。乗換は。朝は座れるのか |
| 「おしゃれなカフェが多い街」 | 住む話ではない。夜に開いている店はあるのか |
| 「family層に人気」 | 学区は。小児科は。公園は。ベビーカーで移動できる地形か |

そして最大の問題は、**弱点が書かれていないこと**。
広告的な文脈で書かれているため、「この街のここが不便」「この条件の人には向かない」が抜ける。
とことん探す人が知りたいのは、まさにそこ。

## 2. 深さを作る16の層

`src/lib/schema.ts` の `DEPTH_FIELDS` が正。各層は「既存記事が書いていないこと」から逆算して決めた。

| 層 | 何を書くか | なぜ必要か |
|---|---|---|
| `faces` | 朝・昼・夜・週末の街の顔 | **内見は昼にする。住むのは夜と週末。**時間帯で街は別物になる |
| `terrain` | 坂・高低差 | 自転車が使えるか、ベビーカーを押せるかが決まる。地図では分からない |
| `noiseSources` | 音が気になりうる場所 | 幹線道路沿い・線路沿い・繁華街隣接は、物件単位で当たり外れが出る |
| `groceries` | 店名・価格帯・徒歩分数 | 「スーパー2軒」では情報にならない。業務スーパーと成城石井では生活コストが違う |
| `residents` | 住民層 | 学生街か、ファミリー中心か、高齢化しているか。街の空気を決める |
| `housingStock` | 物件の傾向 | 築古木造中心かRC中心かで、同じ家賃でも住み心地が変わる |
| `hazards` | 災害リスク | **雰囲気と切り離して判断すべき唯一の項目。**低地・木造密集・液状化 |
| `stationNote` | 駅の使い勝手 | ホームの深さ、改札の位置、乗換の実距離。毎日効く |
| `nightWalk` | 夜の帰り道 | 「治安が良い」の実体。街灯、人通り、遠回りの必要性 |
| `rentReason` | 家賃がその水準である理由 | 安いには理由がある。それを許容できるかが判断の core |
| `neighbours` | 隣の駅との使い分け | **正直に「この用途なら隣がいい」と書く。**これが信頼を作る |
| `outlook` | 5年後どう変わるか | 再開発、路線延伸、家賃の方向。長く住むなら決定的 |
| `exits` | 出口ごとの街の違い（路線ごとに） | **同じ駅でも北口と南口は別の街。**住む方角の選択に直結するのに、駅を一枚岩として扱う既存記事では完全に抜ける。複数路線が乗り入れる駅では改札の位置も出口の先の街並みも路線ごとに変わるため、路線ごとに書く |
| `family` | 学区・保育園・公園・ベビーカー | ファミリーには決定的だが、一般論しか書かれていないことが多い |
| `medical` | 夜間・休日診療、総合病院 | 健康なうちは考えないが、必要になったときに引っ越しはできない |
| `rentRange` | 家賃の幅と、その幅を生む要因 | **相場を1点で示すと同じ駅の中の差が消える。**徒歩分数・築年・通り沿いかで体感が変わる |

これに加えて、必須項目として `tagline` / `summary` / `goodFor` / `notFor` / `residentComment` がある。

## 3. 書き方の規律

### 3.1 固有名詞と数字を必ず入れる

- ✗「駅前にスーパーがある」
- ○「赤札堂 深川店（安い・徒歩6分）、マルエツ プチ（標準・徒歩3分）」

固有名詞が入っていない文は、他の駅に貼り替えても成立してしまう。
**他の駅に貼り替えて成立する文は、書いた意味がない。**

### 3.2 比喩で意味を圧縮しない

最も出やすい失敗がこれである。

- ✗「住むと効くのは半蔵門線と大江戸線の2路線」
- ✗「生活の道具としての性能が高い」「街の空気」「合う人には代えがきかない」
- ○「大手町へも渋谷へも六本木へも乗り換えずに行けるので、転職や異動で通勤先が変わっても引っ越さずに済む」

「効く」は薬に使う言葉で、路線には使わない。何がどうなるのかを書かずに雰囲気だけ伝える文は、
読み手に何も残らない。**誰が・何を・どうして・どうなるのかを省略せずに書く**
（[13-japanese-style-rules.md](./13-japanese-style-rules.md) ルール1・4・5・8）。

この種の表現は AI が書いた文章として広く認識されている。
つまり比喩で圧縮した瞬間に、このサービスが最も避けたい「よくあるまとめ記事」に近づく。

`npm run check:ja` がこの種の語を検出する。検出語は見つけ次第 `scripts/check-japanese.py` に足す。

### 3.3 良し悪しの方向まで書く

述語が曖昧だと、読み手はそれが利点なのか欠点なのか判断できない。

- ✗「夜は森下のほうが開いている」（何が開いているのか。良いことなのか悪いことなのか）
- ○「夜遅くまで営業している飲食店は森下のほうが多い」
- ✗「駅前は流れが速い」 → ○「改札を出た人が立ち止まらずに散っていく」
- ✗「町会が機能している」 → ○「町会が活発に運営され、祭りにも多くの住民が参加している」
- ✗「深川エリアで最も夜が長い」 → ○「深川エリアでは飲食店が最も遅くまで営業している」

主語を書き、その事実が読み手の生活にとって何を意味するのかまで書く。
書いたあとに「これは褒めているのか、けなしているのか」と自問して、
答えられない文は書き直す。

### 3.4 不都合を抽象的な動詞で圧縮しない

弱点を書くときほど、抽象的な述語に逃げやすい。

- ✗「桜の時期に週末の生活が滞る」（通勤が遅れるのか、買い物に行けないのか、道が歩けないのか）
- ○「桜の時期の週末は花見客で混雑し、買い物や外出に不便を感じる」
- ✗「生活に支障が出るほど混む」 → ○「歩道が花見客で埋まり、近所のスーパーへ行くだけでも時間がかかる」
- ✗「週末だけ落ち着かないと感じる」 → ○「週末だけは人混みを歩くことになり、それを負担に感じる」

「滞る」「支障が出る」は、書き手が何を指しているのか決めきれていないときに出てくる。
誰の・どの行動が・どう妨げられるのかを直接書く
（[13-japanese-style-rules.md](./13-japanese-style-rules.md) ルール27）。

### 3.5 地域名を比較の基準にするときは範囲を表す語を付ける

- ✗「個人経営の飲食店の密度は深川で一番高い」
- ○「個人経営の飲食店の密度は深川エリアで一番高い」
- ✗「城南でも指折りの駅だと思う」
- ○「3路線が使えて駅前で買い物が終わるので、城南エリアの中でも暮らしやすい駅だと思う」

「深川」は江東区の町名でもあり、周辺一帯を指す通称でもある。
範囲を表す語を付けないと、町名の中だけの話なのか周辺一帯の話なのかが読み手に伝わらない。
地名そのものを指すとき（「深川に住む世帯」）は付けない（ルール28）。

### 3.6 数量を表す名詞には、何の数量なのかを書く

- ✗「外食と夜の選択肢を求めるなら高円寺を選びたい」（夜の何の選択肢なのか）
- ○「外食できる店の数と、夜遅くまで営業している店の多さを求めるなら高円寺を選びたい」
- ✗「医療の選択肢という点では恵まれている」 → ○「医療機関の選択肢という点では恵まれている」

「選択肢」「多さ」「幅」は、それ自体では中身が決まらない。名詞を並べたときに、
後ろの名詞にだけ「何の」が付いていないことが起きやすい（ルール30）。
略語も同じ理由で開く。「生鮮」ではなく「生鮮品」と書く（ルール31）。

### 3.7 程度の問題を「ない」と言い切らない

- ✗「街そのものに惹かれて選ぶ要素はない」 → ○「街そのものに惹かれて選ぶ要素は少ない」
- ✗「生活に不便はない」 → ○「生活に不便を感じる場面は少ない」

数えて確かめられる不在（「タワーマンションはない」「駅至近に大きな公園はない」）は
そのまま書いてよい。程度でしかないことを言い切ると、読み手が反例を一つ知った時点で
全体の信頼を落とす（ルール29）。

### 3.8 災害は、資料に書いてある事実と、そこから言えることを分けて書く

災害はとくに慎重に書く。書き方ひとつで読み手の受け取り方が大きく変わるためである。
「氾濫が想定されている」と書くと、そこが危険な地域だと読む人が出る。
一方で書かなければ判断材料を奪うことになる。**事実は省かず、評価は加えない。**

- ✗「目黒川の氾濫が想定されており、川沿いの低い区画が浸水想定区域に含まれる」
- ○「目黒区の洪水ハザードマップでは、目黒川沿いの低い区画が浸水想定区域に含まれる。
  これは想定しうる最大規模の降雨を前提にした試算であり、その規模の雨が降れば
  目黒川があふれる可能性がある、という意味である」
- ✗「川沿いの利便性と坂の上の安全性はトレードオフになる」
- ○「坂を上がった区画は想定される浸水の深さが小さくなるため、川沿いの便利さを取るか、
  浸水の想定が小さい坂の上を取るかという選択になる」

ハザードマップの記載は事実として書き、その想定が何を前提にした試算なのかを添える。
「危険」「安全」と評価せず、住所ごとに区のハザードマップを確認するところへ導く（ルール32）。

浸水想定区域が何を意味するかの注記は、駅ページが `dict.hazardNote` として毎回自動で
添えるので、本文で繰り返さない。火災について書く場合は、東京都の地域危険度測定調査が
町丁目ごとに公表している数値を参照先として示す。

### 3.9 条件で変わる結果を言い切らない

- ✗「日比谷線の始発があり、六本木・虎ノ門方面へは座って通勤できる」
- ○「…座って通勤できる。ただしピーク時はホームに列ができ、1本見送ることもある」
- ✗「坂が続く点も、毎日の移動で負担になる」 → ○「…負担に感じる人がいる」

始発駅でもホームに列ができれば1本見送る。坂を負担と感じるかは人によって違う。
断定すると、そうならなかった読み手にとって嘘になる。
`residentComment` は一人の体験として書くものなので、この制限の対象外とする（ルール33）。

### 3.10 費用は、金額が動くことで終わらせず、誰の家計にどう効くのかまで書く

- ✗「駅至近だが価格帯は高く、ここだけで買い物を済ませると食費が上がる」
- ○「…ここだけで買い物を済ませると、平均的な収入の世帯には食費の負担が大きくなる」
- ✗「この街の生活コストの低さを支えている」
- ○「ここを使うかどうかで月々の食費がはっきり変わる」

「食費が上がる」では、いくら上がるのか、それが自分にとって痛い額なのかが読み手に伝わらない。
ただし根拠のない金額（「月に1万円」など）を作ってはいけない。
金額を出せないときは、誰にとっての負担なのかを書いて範囲を示す（ルール34）。

家賃の帯（`rentBands`）が入っている駅では、実額をそちらが示すので、
本文では「その金額が誰にとってどういう意味か」に集中する。

### 3.11 弱点を先に書く

`notFor` と `hazards` と `noiseSources` は、書きにくいほど価値がある。
広告的なトーンに寄った瞬間、既存のまとめ記事と同じものになる。

### 3.12 隣接駅と比較する

単独で「良い街です」と言われても判断できない。
「森下ならもっと安い」「門前仲町のほうが飲食は多いが東西線が厳しい」のように、
**選択肢の中での位置づけ**を書く。

### 3.13 内見では分からないことを書く

内見に行けば分かることを書いても価値は薄い。
価値があるのは、住まないと分からないこと ——
夜8時以降の静けさ、週末の人出、大江戸線ホームの深さ、坂の効き方。

### 3.14 多言語化を前提に書く

日本語話者には自明でも、外国語では説明が要る概念がある
（始発、23区、下町、木造密集、ハザードマップ）。
日本語マスターの段階で **その概念が何であるか**まで書いておくと、
ローカライズが翻訳ではなく本当のローカライズになる（[04-i18n.md](./04-i18n.md)）。

## 4. 「完成」の定義

1駅が完成したと言えるのは、以下をすべて満たしたとき。

- [ ] 16層すべてが埋まっている（`npm run validate:data` が「完成」と表示する）
- [ ] 固有名詞が最低5つ含まれている（店名、通り名、施設名）
- [ ] `notFor` に、書きにくい弱点が最低1つ入っている
- [ ] `neighbours` に、隣接駅のほうが良い用途が1つ以上書かれている
- [ ] 複数路線の駅では、`exits` が路線ごとに書かれている（`npm run validate:data` が抜け漏れを警告する）
- [ ] `hazards` が区のハザードマップで裏取りされている
- [ ] `hazards` に「危険」「安全」の評価語が入っていない（§3.8）
- [ ] 条件や人によって変わることを言い切っていない（§3.9）
- [ ] `npm run check:ja` の確定違反がゼロである
- [ ] 比喩で意味を圧縮した文が1つもない（§3.2）
- [ ] すべての文で、それが利点なのか欠点なのかを読み手が判断できる（§3.3）
- [ ] 不都合を「滞る」「支障が出る」のような抽象的な動詞で圧縮していない（§3.4）
- [ ] 地域名を比較の基準に使う箇所に、範囲を表す語が付いている（§3.5）
- [ ] 「選択肢」「多さ」に、何の選択肢・何の多さなのかが書かれている（§3.6）
- [ ] 程度でしかないことを「ない」と言い切っていない（§3.7）
- [ ] 費用の話が「上がる」で終わらず、誰の家計にどう効くのかまで書かれている（§3.10）
- [ ] `authoredBy` が `human`（`draft` は事実確認前の状態）

## 6. これが448駅に対して意味すること

1駅あたりの記述量は、旧構造のおよそ8〜10倍になる。
448駅すべてをこの基準で書くのは、[11-all-stations-plan.md](./11-all-stations-plan.md) の
試算よりさらに重い。

したがって進め方は次のようになる。

1. **基準を満たした駅から公開する。** 全駅が揃うのを待たない。
   データ構造は既にそれを許している（コンテンツの無い駅はページを生成しない）。
2. **区ごと・路線ごとにまとめて書く。** 隣接駅との比較を書くには、
   隣の駅も同時に調べているほうが速く、質も上がる。
3. **機械で埋まる層（所要時間、スコア2軸）は既に448駅ぶんある。**
   人間は12層の記述に集中する。
4. **多言語展開は、日本語で基準を満たした駅だけを対象にする。**
   浅い日本語を翻訳しない。
