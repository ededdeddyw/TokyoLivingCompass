# 多言語方針

---

## 0. 順序: 日本語で作り切ってから多言語へ

**実運用ロケールは `ja` / `en` / `zh-Hans` / `ko` の4つ**（2026-09-13 に3言語を開いた）。

既存の不動産まとめ記事に対する優位は「深さ」でしか作れない。
浅い記事を13言語に翻訳しても、浅い記事が13個になるだけで勝ち筋にならない。
逆に、深い日本語ができていれば、それをローカライズしたものは
その言語圏に存在しない品質のコンテンツになる。

したがって順序は次のとおり。

1. 日本語で [12-quality-standard.md](./12-quality-standard.md) の基準を満たす
2. 基準を満たした駅だけを多言語展開の対象にする
3. 浅い日本語は翻訳しない

日本語で458駅を作り切ったので、英語・簡体字中国語・韓国語を開いた。
在留外国人の数が多い順に3言語を選んでいる。残る言語は構造としては対応済みで
（`PLANNED_LOCALES`）、URL 設計もそのままなので、開くときに URL を変える必要はない。

---

## 1. 「翻訳」ではなく「ローカライズ」

構想 §4.3 のとおり、目的は日本語記事の翻訳ではなく**各言語ユーザー向けに書き直すこと**。

例: 「駅前に西友がある」

- 日本語話者には十分な情報。
- 英語話者には `Seiyu (a large national supermarket chain, open 24h)` のように補足が要る。
- 一方で「23区」「城南」「始発」などは、日本人には自明でも外国語では説明が要る。

したがって `data/content/{locale}/` は同一構造の**別コンテンツ**であり、日本語ファイルの機械翻訳ではない。

---

## 2. 対応言語

### 実運用
`ja` / `en` / `zh-Hans` / `ko`

### 構造として対応（順次追加）
`zh-Hant` / `vi` / `th` / `id` / `ne` / `tl` / `fr` / `es` / `de` / `pt`

ロケール定義の正は [`src/lib/i18n.ts`](../src/lib/i18n.ts)。

---

## 3. URL 設計

全ページが locale prefix を持つ。日本語も例外にしない（`/ja/...`）。ルート `/` は言語判定してリダイレクトする。

```
/ja/stations/nishimagome
/en/stations/nishimagome
/zh-Hans/stations/nishimagome
```

理由: 後から prefix を足すと URL が全て変わり、SEO 資産を失うため、最初から入れておく。

---

## 4. hreflang

各ページで、そのページが存在する全ロケールの `alternate` を出力する。存在しないロケールは出力しない（空ページへの誘導を防ぐ）。`x-default` は `en` を指す。

---

## 5. 翻訳欠落の扱い

ある駅の `en` コンテンツが未整備の場合:

- 日本語にフォールバックして表示することは**しない**（英語ユーザーに日本語を見せるのは体験として最悪であり、SEO 上も重複扱いになる）。
- 該当ロケールでは、その駅ページを**生成しない**。
- 一覧・検索結果からも除外する。

これにより「翻訳が追いついた駅から順に公開される」という運用になる。

---

## 6. UI 文言

散文（駅コンテンツ）と UI 文言は別管理。UI 文言は [`src/lib/dictionaries.ts`](../src/lib/dictionaries.ts) にロケールごとのフラットな辞書として持つ。

---

## 7. 地名の書き方

駅名・路線名・区名を各言語でどう書くかは、**確認できる訳名を持っているかどうか**で決める。
もっともらしい訳名を作ってはいけない（[13-japanese-style-rules.md](./13-japanese-style-rules.md) ルール35）。
読み手はその駅へ行こうとするので、実在しない表記を出せば即座に気づかれる。

| | 駅名 | 路線名 | 区名 |
|---|---|---|---|
| `en` | ローマ字（出典データが持つ） | 英語名（出典データが持つ） | `Chiyoda City` の形 |
| `zh-Hans` | 日本語の表記のまま | 日本語の表記のまま | 日本語の表記のまま |
| `ko` | 日本語の表記のまま | 日本語の表記のまま | 韓国語表記（23件の一覧を持つ） |

簡体字中国語と韓国語で駅名・路線名を日本語のままにしているのは、
確認できる訳名の一覧を持っていないためである。駅の看板に出ている表記を
そのまま渡すことになるので、読み手が駅を取り違えることはない。
訳名の一覧を出典つきで用意できたら、そのときに切り替える。

韓国語は、前の語の終わりが子音か母音かで助詞の形が変わる（이/가、은/는、과/와）。
駅名が日本語の表記のままでは形を決められないので、
形が変わらない助詞（에서、보다、까지）を使う言い回しにしてある。

---

## 8. データから組み立てる層と、書く層

458駅のうち441駅は、出典のあるデータから機械的に組み立てている
（`scripts/build-station-content.py`）。この層は**翻訳していない**。
同じデータから、言語ごとの文型で書き起こしている。
文型は [`scripts/station_phrases.py`](../scripts/station_phrases.py) にまとめてあり、
言語を1つ足すときは同じキーの文型をすべて埋める。埋め忘れは起動時に見つかる。

人が書いた17駅だけは、文型では作れない。この17駅は §9 の手順でローカライズする。

---

## 9. AI によるローカライズのフロー

1. 日本語マスターを人間が書く。
2. 構造化データ（スコア・家賃・通勤）は言語非依存なので翻訳不要。
3. 散文のみ、ロケールごとに AI がローカライズする。プロンプトには対象読者の前提知識を明示する。
4. 生成物は `authoredBy: "ai-localized"` として記録する。
5. `residentComment`（在住者コメント）だけは、ニュアンスが命なので AI 生成の後に人間レビューを必須とする。
6. マスターデータ更新時、影響する全ロケールのコンテンツを再生成対象としてフラグする。
