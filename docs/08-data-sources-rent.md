# 家賃相場データの出典

[06-roadmap.md](./06-roadmap.md) Phase 1 の先送り論点「家賃データの出典」の調査結果と決定。

調査日: 2026-09-06

---

## 0. 結論（先に）

| | 採用 | 役割 |
|---|---|---|
| 主データ | **商用の賃料統計データ（アットホーム系）を購入** | 駅別・間取り別の家賃相場の実値 |
| 検算 | **住宅・土地統計調査（e-Stat）** | 区単位での妥当性チェック。無料 |
| 並行 | **不動産会社との提携** | 送客先の開拓と同時に進める。成立すれば主データを置き換えうる |
| 不採用 | 不動産情報ライブラリ API / LIFULL HOME'S データセット / ポータルのスクレイピング | 理由は §2 |

**採用する家賃の定義は「募集賃料（asking rent）」**とし、それをサイト上で明示する（§3）。

---

## 1. 前提：「家賃相場」には3つの異なる数字がある

ここを混ぜると、出典を揃えても数字が合わない。

| 種類 | 意味 | 主な出所 | 性質 |
|---|---|---|---|
| **募集賃料** | いま募集中の物件の提示額 | 不動産ポータル、業者間データ | 実際の成約額より**高め**に出る |
| **成約賃料** | 実際に契約が成立した額 | REINS、業者の成約データ | 最も実態に近いが、入手に宅建業免許が要る |
| **支払家賃** | いま住んでいる人が払っている額 | 住宅・土地統計調査 | 古い契約を含むため**低め**に出る |

本サービスのユーザーは「これから借りる人」なので、**募集賃料**が意思決定に最も近い。ただし成約額より高めに出ることを明示する必要がある（§3）。

## 2. 候補の評価

### A. 国土交通省 不動産情報ライブラリ API — 不採用

2024年4月提供開始の公的 API。無料、商用利用可。

**しかし賃貸データを含まない。** 提供されるのは不動産取引価格情報（＝売買）、地価公示、都道府県地価調査、都市計画情報など。取引価格情報は売買取引の当事者アンケートに基づくもので、賃料は対象外。

→ 家賃には使えない。将来「地価から街のグレードを補正する」といった用途はありうる。

### B. 総務省 住宅・土地統計調査（e-Stat） — 検算用に採用

- 粒度: **市区町村**（駅単位ではない）
- 周期: **5年**（最新は令和5年＝2023年調査）
- 種類: **支払家賃**（§1）
- 費用: 無料。政府統計なので出典明示のうえ利用可

駅別の相場としては粒度も鮮度も足りないが、**「区単位の平均から極端に外れていないか」の検算には使える**。商用データを買ったあと、その値が公的統計と整合するかを機械的に確認する層として組み込む。

### C. LIFULL HOME'S データセット（国立情報学研究所 IDR） — 不採用

賃貸物件約533万件のスナップショットと月次データ、間取り図画像まで含む極めて質の高いデータセット。

**ただし提供対象は学術機関の研究者。** 本サービスのような商用利用は原則対象外（個別の事前手続き・審査で認められる場合はあるとされるが、事業の基盤データとして当てにできる性質のものではない）。

→ 商用サービスの基盤には使えない。

### D. 商用の賃料統計データ（アットホーム系） — 主データとして採用

アットホームが法人向けに提供している賃料統計データ群。

- **アパート・マンション統計データ**: 全国の**町丁単位**で、賃料・専有面積・平米単価・築年数・募集期間の平均値。**間取りごと**の募集賃料推移、3年前・5年前との比較も可能。全国57,000店以上の加盟店から公開・募集された物件情報を集計したもので、データ構築・集計は日本統計センターが行っている。
- **賃料・空室率推計サービス**: 「駅」で範囲指定して推計賃料・推計空室率を確認できる。
- **マンション賃料インデックス**

株式会社タスの TAS-MAP もアットホームの賃貸データを統計分析して賃料査定を行っており、この系統のデータが業界の事実上の標準になっている。

**本サービスの要件との適合**
- 間取り別（1R / 1K / 1LDK / 2LDK）→ 対応可
- 駅別 → 町丁単位のデータを駅の徒歩圏に集約する必要がある（§4）
- 商用利用・Web 公開 → **契約条件の確認が必須**（§5）

> 注: 価格と正確な利用条件は本調査では確認できていない（開発環境のネットワーク制限でベンダーのサービスページを直接参照できなかった）。**見積もりと利用許諾範囲の確認は営業窓口への直接問い合わせが必要**。これが Phase 1 の最初のアクション。

### E. 不動産ポータルのスクレイピング — 不採用

技術的には可能だが、商用サービスの基盤としては採らない。

- 主要ポータルの robots.txt は検索結果・物件詳細ページ等へのクロールを制限している
- 収集データの再配布・商用利用は著作権上の争点になりうる
- 継続的なアクセスは業務妨害と評価されるリスクがある
- 加えて、**送客先として提携したい相手のサイトを無断収集するのは、事業として筋が悪い**（構想 §16 の収益モデルと正面から矛盾する）

法的にグレーな部分を抱えたまま SEO で露出を増やすのは、事業リスクの取り方として割に合わない。

### F. 不動産会社との提携 — 並行して進める

構想 §16 の収益モデルは不動産会社への送客。**データをもらう相手と、送客する相手は同じ**である。

つまりデータ調達の交渉は、そのまま収益の交渉になる。外国人対応の賃貸仲介会社1社と組めれば、

- 募集中物件の実データ（募集賃料・成約賃料の両方）
- 送客の受け皿
- 「外国人生活適性」スコアの一次情報（実際に外国人が入居できる物件の割合）

が同時に手に入る。**Phase 1 で商用データを買うのと並行して、提携先の開拓を始めるべき。** 提携が成立すれば D を置き換えられる可能性がある。

## 3. 表示上の約束

家賃の数字は、それが何の数字かを示さないと誤解を生む。駅ページには必ず以下を出す。

- 「募集賃料」であること（成約額はこれより下がりうること）
- 出典名と取得時点
- 算出方法（どの範囲の物件の、どの代表値か）

これは信頼性の担保であると同時に、内容の薄い競合との差別化になる。数字の出所を示せるサイトは多くない。

---

## 4. 町丁データを駅別に変換する方法

購入できるデータは町丁単位、本サービスが必要なのは駅単位。変換規則を先に決めておく。

1. 各駅に代表点（駅の座標）を持たせる。
2. 駅から**徒歩圏（半径 800m を基本）**に重心が含まれる町丁を抽出する。
3. 間取りごとに、町丁の賃料を**面積または戸数で加重平均**する。
4. サンプル数が閾値（暫定 30件）に満たない間取りは、値を出さず「データなし」として扱う。
5. 半径・加重方法・閾値は `docs` に記録し、変えたら再計算する。

代表値は**平均ではなく中央値**を優先する。賃貸市場は高額物件が裾を引くため、平均は実感より高く出る。購入データが平均しか持たない場合は、その旨を出典表示に含める。

## 6. データ構造への反映（実装済み）

`src/lib/schema.ts` に `sources.rent` を追加した。

```jsonc
"sources": {
  "rent": {
    "name": "出典名",
    "url": "https://...",          // 任意
    "basis": "asking",             // asking | contracted | paid（§1）
    "statistic": "median",         // median | mean
    "retrievedAt": "2026-09-06",
    "method": "radius-800m-weighted",   // 任意。RENT_METHODS の ID
    "sampleSize": 320                   // 任意
  }
}
```

`method` は自由記述ではなく `RENT_METHODS` の ID にしてある。散文にすると多言語で表示できないため、
表示ラベルは `src/lib/dictionaries.ts` にロケールごとに持つ。

`npm run validate:data` は、**`dataQuality` が `seed` 以外の駅に `sources.rent` がなければエラーにする**。
出典のないデータを "reviewed" に昇格させられない、という制約をビルドで担保する。

駅ページの家賃セクションには、出典・取得時点・「何の家賃か」・算出方法が表示される。
出典が未設定の駅は「家賃の出典は未設定です」と出る。
