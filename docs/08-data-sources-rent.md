# 家賃相場データの出典

[06-roadmap.md](./06-roadmap.md) Phase 1 の先送り論点「家賃データの出典」の調査結果と決定。

調査日: 2026-09-06（2026-09-12 に家賃の推移を追記。2026-09-13 に、458駅ぶんの取得方法と出典3社への変更を反映）

---

## 0. 結論（先に）

| | 採用 | 役割 |
|---|---|---|
| 主データ（本命） | **商用の賃料統計データ（アットホーム系）を購入** | 駅別・間取り別の家賃相場の実値 |
| 主データ（暫定） | **3社が公開する駅の家賃相場を読み取り、平均して1万円刻みの帯にする** | 購入までのつなぎ。出典を明示して「当社調べ」として出す（§E-2） |
| 検算 | **住宅・土地統計調査（e-Stat）** | 区単位での妥当性チェック。無料 |
| 並行 | **不動産会社との提携** | 送客先の開拓と同時に進める。成立すれば主データを置き換えうる |
| 不採用 | 不動産情報ライブラリ API / LIFULL HOME'S データセット / ポータルの自動収集 | 理由は §2 |

**採用する家賃の定義は「募集賃料（asking rent）」**とし、それをサイト上で明示する（§3）。

---

## 1. 前提：「家賃相場」には3つの異なる数字がある

ここを混ぜると、出典を揃えても数字が合わない。

| 種類 | 意味 | 主な出所 | 性質 |
|---|---|---|---|
| **募集賃料** | いま募集中の物件の提示額 | 不動産ポータル、業者間データ | 実際の成約額より**高め**に出る |
| **成約賃料** | 実際に契約が成立した額 | REINS、業者の成約データ | 最も実態に近いが、入手に宅建業免許が要る |
| **支払家賃** | いま住んでいる人が払っている額 | 住宅・土地統計調査 | 古い契約を含むため**低め**に出る |

本サービスのユーザーは「これから借りる人」なので、**募集賃料**が意思決定に最も近い。ただし成約額より高めに出ることを明示する必要がある（§3）。

## 2. 候補の評価

### A. 国土交通省 不動産情報ライブラリ API — 不採用

2024年4月提供開始の公的 API。無料、商用利用可。

**しかし賃貸データを含まない。** 提供されるのは不動産取引価格情報（＝売買）、地価公示、都道府県地価調査、都市計画情報など。取引価格情報は売買取引の当事者アンケートに基づくもので、賃料は対象外。

→ 家賃には使えない。将来「地価から街のグレードを補正する」といった用途はありうる。

### B. 総務省 住宅・土地統計調査（e-Stat） — 検算用に採用

- 粒度: **市区町村**（駅単位ではない）
- 周期: **5年**（最新は令和5年＝2023年調査）
- 種類: **支払家賃**（§1）
- 費用: 無料。政府統計なので出典明示のうえ利用可

駅別の相場としては粒度も鮮度も足りないが、**「区単位の平均から極端に外れていないか」の検算には使える**。商用データを買ったあと、その値が公的統計と整合するかを機械的に確認する層として組み込む。

### C. LIFULL HOME'S データセット（国立情報学研究所 IDR） — 不採用

賃貸物件約533万件のスナップショットと月次データ、間取り図画像まで含む極めて質の高いデータセット。

**ただし提供対象は学術機関の研究者。** 本サービスのような商用利用は原則対象外（個別の事前手続き・審査で認められる場合はあるとされるが、事業の基盤データとして当てにできる性質のものではない）。

→ 商用サービスの基盤には使えない。

### D. 商用の賃料統計データ（アットホーム系） — 主データとして採用

アットホームが法人向けに提供している賃料統計データ群。

- **アパート・マンション統計データ**: 全国の**町丁単位**で、賃料・専有面積・平米単価・築年数・募集期間の平均値。**間取りごと**の募集賃料推移、3年前・5年前との比較も可能。全国57,000店以上の加盟店から公開・募集された物件情報を集計したものである。データの構築と集計は日本統計センターが行っている。
- **賃料・空室率推計サービス**: 「駅」で範囲指定して推計賃料・推計空室率を確認できる。
- **マンション賃料インデックス**

株式会社タスの TAS-MAP も、アットホームの賃貸データを統計分析して賃料査定を行っている。この系統のデータが、業界の事実上の標準になっている。

**本サービスの要件との適合**
- 間取り別（1R / 1K / 1LDK / 2LDK）→ 対応可
- 駅別 → 町丁単位のデータを駅の徒歩圏に集約する必要がある（§4）
- 商用利用・Web 公開 → **契約条件の確認が必須**（§5）

> 注: 価格と正確な利用条件は本調査では確認できていない（開発環境のネットワーク制限でベンダーのサービスページを直接参照できなかった）。**見積もりと利用許諾範囲の確認は営業窓口への直接問い合わせが必要**。これが Phase 1 の最初のアクション。

### E. 不動産ポータルの自動収集（スクレイピング） — 不採用

物件一覧や物件詳細を機械で巡回して集めることは採らない。

- 主要ポータルの robots.txt は検索結果・物件詳細ページ等へのクロールを制限している
- 継続的なアクセスは業務妨害と評価されるリスクがある
- 加えて、**送客先として提携したい相手のサイトを無断収集するのは、事業として筋が悪い**（構想 §16 の収益モデルと正面から矛盾する）

### E-2. 各サイトが公開している「駅の家賃相場」を読み取る — 採用（暫定の主データ）

E と混同しやすいが、別のことである。LIFULL HOME'S・Yahoo!不動産・アットホームは、
物件一覧とは別に**駅ごとの家賃相場ページを公開している**。そこに出ている値は、
各社が自社の掲載物件を集計した統計であり、物件データそのものではない。

これを出典・URL・取得日とともに記録し、複数サイトの平均を取り、
1万円刻みの帯に丸めて「当社調べ」として出す。

**取得は `scripts/fetch-rent.py` が行う。**17駅のうちは人がページを開いて
記録していたが、458駅では手が回らないため、スクリプトで取りに行くことにした。
E との違いは変わらず、取りに行くのは駅ごとの統計ページだけで、物件一覧は
1ページも開かない。そのうえで次の3つを守る。

1. robots.txt を確認し、統計ページを制限していないことを確かめてから取りに行く。
2. 1駅ずつ間を空け、サイトごとに間隔を変えながら進める。
3. 相手が「速すぎる」と返してきたら、間隔を広げる。

**LIFULL HOME'S からは、途中で取れなくなった。**200件ほど取ったところで、
どのページを開いても HTTP 202 と空の応答が返るようになった。間隔を90秒まで
広げても変わらず、このIPアドレスからの取得を止めていると判断した。
1社だけでは「複数サイトの平均」と名乗れないため、3社目としてアットホームを
加えている。時間をおいて LIFULL HOME'S を取り直せたら、3社の平均に戻す。

**各社のページには「無断転載を禁止します」と書かれている。**したがって、
どこか1社の数字をそのまま載せることはしない。駅ページに出すのは3社（または2社）の
平均を1万円刻みに丸めた帯であり、各社の元の値は `data/rent-survey/` に
出典として控えるだけで、サイトには出さない。

**元の値をリポジトリに残す判断について**（2026-09-13）。
このリポジトリは非公開のまま運用する。そのうえで、各社の元の値は
`data/rent-survey/` に残す。「当社調べ」と名乗る以上、帯のもとになった数字を
あとから検算できる状態にしておく価値のほうが大きいと判断した。
リポジトリを公開することになったら、この判断をやり直す。
そのときは、元の値を非公開の場所へ移すか、帯だけを残すことになる。

**なぜ1点の数字ではなく帯にするのか。**実際に見比べると、同じ駅でもサイトによって
数万円ちがう。中目黒のワンルームは、LIFULL HOME'S が12.7万円、Yahoo!不動産が14.26万円、アットホームが10.84万円だった。
集計する範囲（駅からの距離）も対象物件も違うためで、どちらかが誤っているわけではない。
1点の数字で示すと、この差を読み手から隠すことになる。

**帯の作り方**（`scripts/build-rent-bands.py`）:

1. サイトごとの値を `data/rent-survey/<slug>.json` に記録する。
   出典名・URL・取得日・その値が何を集計したものか（`coverage`）・
   人がページを開いて確認したか（`verified`）を必ず書く。
2. 間取りごとに平均を取り、1万円刻みに切り下げて `low`、その1万円上を `high` とする。
3. **2サイト以上そろわない間取りは帯にしない。**「複数サイトの平均」と名乗る以上、
   1サイトだけの値を平均と呼べないため。
4. 出典間の開きが3万円以上なら `wideSpread` を立て、駅ページで「出典によって差が大きい」と注記する。
5. `verified` が1つでも false なら、駅ページに暫定値と表示する。

`npm run validate:data` が、出典2件未満をエラー、未確認の帯を警告として報告する。

**この方式の限界**は正直に書いておく。各社の集計方法は公開されておらず、
基準をそろえた比較ではない。募集賃料なので成約額より高めに出る。
更新のタイミングもサイトごとに違う。したがってこれは §D の商用データが入るまでの
暫定の主データであり、購入後は置き換える。


技術的には可能だが、商用サービスの基盤としては採らない。

- 主要ポータルの robots.txt は検索結果・物件詳細ページ等へのクロールを制限している
- 収集データの再配布・商用利用は著作権上の争点になりうる
- 継続的なアクセスは業務妨害と評価されるリスクがある
- 加えて、**送客先として提携したい相手のサイトを無断収集するのは、事業として筋が悪い**（構想 §16 の収益モデルと正面から矛盾する）

法的にグレーな部分を抱えたまま SEO で露出を増やすのは、事業リスクの取り方として割に合わない。

### F. 不動産会社との提携 — 並行して進める

構想 §16 の収益モデルは不動産会社への送客。**データをもらう相手と、送客する相手は同じ**である。

つまりデータ調達の交渉は、そのまま収益の交渉になる。外国人対応の賃貸仲介会社1社と組めれば、

- 募集中物件の実データ（募集賃料・成約賃料の両方）
- 送客の受け皿
- 「外国人生活適性」スコアの一次情報（実際に外国人が入居できる物件の割合）

が同時に手に入る。**Phase 1 で商用データを買うのと並行して、提携先の開拓を始めるべき。** 提携が成立すれば D を置き換えられる可能性がある。

### G. 家賃の推移（時系列）— D に含めて購入する

「いま家賃がいくらか」だけでは、上がっているのか下がっているのかが読み手に分からない。
**「いま高い」と「これから高くなる」は、住む場所を決める判断としてまったく違う。**
したがって、間取り別の相場に加えて、5年程度の推移を持つ。

アットホームの「アパート・マンション統計データ」は、町丁別・時系列・専有面積別の平均賃料を
Excel または CSV で提供している。§D で購入するデータに時系列を含める形で調達する。
新たな契約先を増やす必要はない。

購入時に確認する項目:

- 時系列がさかのぼれる年数（5年に届くか）
- 集計の粒度（年単位か四半期単位か）
- 間取り別に取れるか、専有面積別しか取れないか（後者なら間取りへの読み替え規則を決める）
- Web サイト上での公開可否（§D と同じ論点。ここが通らなければ推移も載せられない）

## 3. 表示上の約束

家賃の数字は、それが何の数字かを示さないと誤解を生む。駅ページには必ず以下を出す。

- 「募集賃料」であること（成約額はこれより下がりうること）
- 出典名と取得時点
- 算出方法（どの範囲の物件の、どの代表値か）

これは信頼性の担保であると同時に、内容の薄い競合との差別化になる。数字の出所を示せるサイトは多くない。

## 4. 町丁データを駅別に変換する方法

購入できるデータは町丁単位、本サービスが必要なのは駅単位。変換規則を先に決めておく。

1. 各駅に代表点（駅の座標）を持たせる。
2. 駅から**徒歩圏（半径 800m を基本）**に重心が含まれる町丁を抽出する。
3. 間取りごとに、町丁の賃料を**面積または戸数で加重平均**する。
4. サンプル数が閾値（暫定 30件）に満たない間取りは、値を出さず「データなし」として扱う。
5. 半径・加重方法・閾値は `docs` に記録し、変えたら再計算する。

代表値は**平均ではなく中央値**を優先する。賃貸市場は高額物件が裾を引くため、平均は実感より高く出る。購入データが平均しか持たない場合は、その旨を出典表示に含める。

## 6. データ構造への反映（実装済み）

`src/lib/schema.ts` に `sources.rent` を追加した。

```jsonc
"sources": {
  "rent": {
    "name": "出典名",
    "url": "https://...",          // 任意
    "basis": "asking",             // asking | contracted | paid（§1）
    "statistic": "median",         // median | mean
    "retrievedAt": "2026-09-06",
    "method": "radius-800m-weighted",   // 任意。RENT_METHODS の ID
    "sampleSize": 320                   // 任意
  }
}
```

`rentHistory` も追加した。推移は本文で「上昇が続いている」と言い切る材料になるため、
出典を任意ではなく必須にしてある。

```jsonc
"rentHistory": {
  "points": [
    { "year": 2021, "rent": { "oneRoom": 89000, "oneLDK": 168000 } },
    { "year": 2026, "rent": { "oneRoom": 98000, "oneLDK": 195000 } }
  ],
  "source": { "name": "...", "basis": "asking", "statistic": "median",
              "retrievedAt": "2026-09-12" }
}
```

間取りごとに欠けがあってよい。値が1つも入っていない間取りは、駅ページの表に列を出さない。

`method` は自由記述ではなく `RENT_METHODS` の ID にしてある。散文にすると多言語で表示できないため、
表示ラベルは `src/lib/dictionaries.ts` にロケールごとに持つ。

`npm run validate:data` は、**`dataQuality` が `seed` 以外の駅に `sources.rent` がなければエラーにする**。
出典のないデータを "reviewed" に昇格させられない、という制約をビルドで担保する。

駅ページの家賃セクションには、出典・取得時点・「何の家賃か」・算出方法が表示される。
出典が未設定の駅は「家賃の出典は未設定です」と出る。

## 7. 実行環境からの通信（2026-09-13 時点）

以前はこのリモート実行環境の外部通信がネットワークポリシーで遮断されており、
`raw.githubusercontent.com` 以外はゲートウェイが 403 を返していた。
環境の設定を変えてもらったことで、いまは各サイトの相場ページを取りに行ける。

ただし取得側の制限は残る。

| ホスト | 状態 |
|---|---|
| `realestate.yahoo.co.jp` | 5〜8秒の間隔で取得できる |
| `www.athome.co.jp` | 取得できる |
| `www.homes.co.jp` | 200件ほど取ったところで HTTP 202 と空の応答になった。間隔を90秒に広げても戻らない |

したがって家賃データが載らない理由は、**§D の商用データをまだ購入していないこと**に絞られる。
無償のデータ（e-Stat の区別家賃、地価公示）を取り込む検算層は、いつでも着手できる。

## 8. 家賃相場を取得する手順（§E-2 の実務）

```bash
python3 scripts/build-rent-sources.py      # 駅コードを集めて sources.json に書く
python3 scripts/fetch-rent.py              # 各駅の相場ページから間取り別の値を取る
python3 scripts/build-rent-bands.py        # 1万円刻みの帯にまとめる
python3 scripts/apply-rent.py              # 駅プロフィールに書き込む
npm run validate:data                      # 警告が消えたことを確かめる
```

**駅コード**（`data/rent-survey/sources.json`）はサイトごとに形が違う。

| サイト | URL の形 | コードの取り方 |
|---|---|---|
| LIFULL HOME'S | `/chintai/tokyo/<ローマ字>_<番号>-st/price/` | 路線ごとの相場一覧ページから読み取る |
| Yahoo!不動産 | `/rent/price/03/13/r/<路線>/<駅>/` | 路線ごとの相場一覧ページから読み取る |
| アットホーム | `/chintai/souba/tokyo/<ローマ字>-st/` | ロースターのローマ字から組み立てる |

**読み取るのは、絞り込み条件の掛かっていない駅全体の相場**である。
SUUMO を使わないのは、駅の相場ページに「指定なし」の選択肢がなく、
新築かつ徒歩1〜5分に固定されているためである（§9）。

**サイトを1つ足すときは、次の順で確かめる。**

1. robots.txt に、その統計ページを制限する記述がないか。
2. ページに書かれている集計の条件（対象期間・対象物件）。これを `coverage` に写す。
   自分の言葉で言い換えず、サイトの注記のとおりに書く。
3. 1駅ぶん取って、ほかのサイトの値と桁が合うか。

`coverage` を必ず書くのは、あとから見たときに「この数字は何を集計したものだったか」が
分からなくなるのを防ぐためである。「当社調べ」と名乗る以上、元の観測値をリポジトリに残し、
第三者が同じ手順をたどれる状態にしておく。

## 9. SUUMO を使わない理由

SUUMO の駅別相場ページ（`/chintai/soba/tokyo/ek_<駅コード>/`）には、
絞り込みに「指定なし」の選択肢がなく、新築かつ駅徒歩1〜5分の物件だけが対象になる。
中目黒のワンルームは17.6万円と出たが、同じ駅で LIFULL HOME'S が12.7万円、
Yahoo!不動産が14.26万円だった。条件がそろわない値を平均に混ぜると、
帯そのものが上振れする。したがって出典から外している。
