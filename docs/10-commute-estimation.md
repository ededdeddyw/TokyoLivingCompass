# 所要時間の計算方法

443駅 × 7オフィス街 = 3,101件の所要時間を、鉄道networkの最短経路として計算している。

生成: `python3 scripts/build-commutes.py` → `data/computed/commutes.json`

---

## 1. なぜ計算するのか

経路検索の商用APIやGTFSを使うのが正確だが、443駅ぶんとなると件数が多く、ライセンスと費用が読めない。
一方で所要時間は逆引き検索の中心的な絞り込み条件なので、無いままでは機能しない。

そこで**公開データから計算し、精度を実測で確かめたうえで使う**方針を採った。
将来API等に置き換える場合も、この計算値が精度の下限を保証する。

---

## 2. 計算モデル

### network

- ノードは **(駅グループ, 路線) の組**。単に駅をノードにすると乗換回数を数えられない。
- 同じ駅の別路線どうしを**乗換辺**でつなぐ。
- 隣接駅間の所要時間 = 距離 ÷ 路線種別ごとの表定速度 + 停車時間。
- 距離は緯度経度から求めた直線距離を **1.15倍**（線路の曲がりを見込む）。

### パラメータ

| 項目 | 値 |
|---|---|
| 既定の表定速度 | 35 km/h |
| 停車時間 | 1駅あたり 0.4分 |
| 乗り換え | 1回あたり 5分（徒歩＋待ち） |
| 最初の待ち時間 | 0分 |

路線ごとの速度は `LINE_SPEED` に定義。中央線快速45、都電荒川線13、つくばエクスプレス55など。

**最初の待ち時間を0にしている**のは、世間で言う「新宿まで5分」が乗車時間を指すため。ここを揃えないと利用者の感覚とずれる。

### 経路選択

オフィス駅から Dijkstra で全駅への最短時間を求める。乗り換えにも時間（5分）を課しているので、時間だけを最小化して乗換だらけの経路が選ばれることはない。

---

## 3. 精度

実際の所要時間が分かっている18区間と比較した。

| 指標 | 値 |
|---|---|
| 平均誤差 | **+0.8分** |
| 範囲 | −2分 〜 +4分 |
| 誤差±3分以内 | **17 / 18** |

例（実際 → 計算）: 高円寺→新宿 8→8 / 清澄白河→大手町 10→8 / 中目黒→渋谷 3→4 / 大井町→品川 6→5 / 蒲田→品川 13→15。

「30分以内」といった絞り込みには十分な精度がある。

---

## 4. 限界（把握しているもの）

1. **優等列車を考慮していない。** 各駅停車ベースで計算しているため、急行・快速が停まる駅は実際より遅く出る。東急東横線・京王線・小田急線など優等の効果が大きい路線は表定速度を上げて補正しているが、その路線の各停しか停まらない駅は逆に速く出る。誤差+4分だった浅草→大手町、+3分だった自由が丘→渋谷がこの型。
2. **時間帯を区別していない。** 朝ラッシュの増発・遅延は反映していない。
3. **駅までの徒歩時間を含まない。** 駅から駅までの時間である。
4. **直通運転を路線単位でしか扱っていない。** 実際には直通で乗換不要な区間が、計算上は乗換1回になることがある。この場合は実際より遅く出る。
5. **距離が直線ベース。** 大きく迂回する路線では過小に出る。

いずれも「実際より遅めに出る」方向の誤差が多く、利用者に対して過大な期待を持たせない側に倒れている。

---

## 5. サイト上の表示

駅ページの都心アクセス欄に、計算値であることと乗換5分を算入していることを明記している。数字の出所を示さずに出さない、という方針（[08-data-sources-rent.md](./08-data-sources-rent.md) §3）は所要時間にも同じく適用する。

---

## 6. スコアへの利用

この所要時間から `commute` 軸のスコアを計算している（`scripts/build-scores.py`）。

7つのオフィス街への所要時間の**平均**を使う。1箇所に速いだけの駅より、どこへでも出やすい駅を高く評価するため。平均8分を100として、そこから24分ごとに半減する曲線にしている（直線だと平均50分あたりで0に張り付き、郊外側の駅を区別できなくなる）。
