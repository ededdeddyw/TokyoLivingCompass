# 開発の原則と、これまでに決めたこと

**作業を始める前に、この文書を読む。**

セッションごとに自動で読み込まれるのは `CLAUDE.md` だけである。
日本語の書き方は `CLAUDE.md` と [13-japanese-style-rules.md](./13-japanese-style-rules.md) にある。
この文書には、それ以外の判断の方針をまとめる。細かい根拠は §6 の各文書にある。

---

## 1. 何を作っているのか

物件を探す**前に**、住む街を決めるための意思決定エンジンである。
部屋ではなく街を選ぶ段階の読み手に向ける（[00-concept.md](./00-concept.md)）。

既存の不動産まとめ記事に対する優位は、深さでしか作れない。
浅い記事を13言語に翻訳しても、読み手の判断を助けない。
**まず日本語で作り切り、多言語展開はそのあとにする。**

対象は東京23区の458駅である。一部を駅名だけで留める案は採らない
（[11-all-stations-plan.md](./11-all-stations-plan.md)）。

## 2. 判断の原則

迷ったときは、この11個で決める。

### 2.1 確認できない固有名詞と数字は書かない

店名・施設名・数字は、出典で確認してから書く。確認できないものは削る。
それらしい名前を置いてはいけない。読み手はその店に行こうとするので、
実在しなければ即座に気づく。一つ見つかった時点で、他の記述もすべて疑われる。

`groceries` の各店は `sourceUrl` と `verifiedAt` が必須で、
確認していない店はデータとして持てない。

### 2.2 数は絶対値ではなく、駅どうしの相対的な位置で点にする

東京では、スーパーを6軒で頭打ちにしただけで446駅中236駅が90点台になった。
どの軸も「23区内の何割の駅より多いか」で点をつける。

ただし**多いほどよいとは限らない軸では、相対評価をそのまま使わない**（§3.3）。

### 2.3 機械で出せる軸は機械で出し、人の判断が要る軸に人を集中させる

18軸のうち16軸を機械で埋めた。残るのは `style` と `internationalFriendliness` の2軸である。
人間が判断する軸をここまで絞れたことが、458駅を現実的にしている。

### 2.4 出典のある数字と、人が書く文章を混ぜない

朝の混雑率は全458駅ぶんあるが、人が書く17層の充足率には入れない。
混ぜると、書けている駅の数が実態より多く見える。
`npm run validate:data` が層ごとに分けて数える。

### 2.5 画面に出す同じ名前の数字は、定義を1つにする

一覧で区分を選ぶと雪が谷大塚は総合評価7.1と出るのに、駅ページでは5.2と出ていた。
どちらも正しい計算だったが、読み手にはどちらを信じればよいか分からない。
同じ名前の数字を2つの定義で出さない。出すなら、どの前提で出した数字かを
その場に書く（`src/components/OverallScore.tsx`）。

### 2.6 派生値は保存せず、毎回計算する

総合評価・グレード・適合度は、重みが変われば変わる。データには持たせない
（[07-architecture.md](./07-architecture.md)）。

### 2.7 データが語れないことは、書かずに未着手として残す

保育園の定員も待機児童数も持っていない。だから定員の多さには触れない。
根拠のない評価語を出すほうが、書かないより悪い。

### 2.8 評価語を加えない。事実と、そこから言えることを分ける

災害はとくに慎重に扱う。「危険」「安全」と評価せず、
ハザードマップの記載を事実として書き、その想定が何を前提にした試算なのかを添える。
そのうえで、誰にとって何の判断材料になるのかまで書く。
ここまで書かないと読み手の判断を助けないが、ここから先は書き手の感想になる。

### 2.9 読み手に見せる日本語は、ですます調で書く

駅ページの本文も、画面の文言も、利用者への報告も、すべてですます調で書く。
読み手に向けて書くものだからである。`docs/` の設計文書とコード中のコメントは、
書き手どうしの記録なので、である調のままにする
（[13-japanese-style-rules.md](./13-japanese-style-rules.md) ルール47）。

### 2.10 読み手の区分を先に決めてから、その中で比べる

458駅を1つの総合点で並べない。世帯・夜の過ごし方・家賃と立地の3軸で8区分に分け、
その区分の中だけで比べる（[14-audience-segments.md](./14-audience-segments.md)）。

### 2.11 失敗を見つけたら、直して、ルールにして、機械で検出できるようにする

日本語表現ルールは49項目あるが、どれも実際に書いた文章の失敗から足した。
機械で判定できるものは `npm run check:ja` に入れる。
論旨に関わるものは機械では見られないので、書いたあとに読み返して自分で確かめる。

## 3. 測り方で繰り返した失敗

同じ失敗を繰り返さないために、原因と対処を残す。
詳しい数字は [03-scoring.md](./03-scoring.md) §4 にある。

### 3.1 OpenStreetMap の登録の細かさは、区によって20倍違う

駅から500m以内の商業の建物の棟数は、中央値で台東区205棟に対して板橋区9棟である。
`food` スコアの中央値も台東区93に対して足立区16と開く。
都心に店が多いのは事実だが、**この開きの一部は地図を作った人の多さの差である。**

武蔵小山は300m以内の飲食店が19軒しか登録されていない。
全長約800mのアーケード商店街がある駅の数としては少なすぎる。

対処: 店の数だけで判断しない。`npm run check:coverage` が、
乗降客数から見て店の登録が少ない駅を並べる。本文に「店が少ない」と書く前に見る。

### 3.2 乗降客数は、駅を通り抜ける人の数でしかない

荻窪は1日21万人が乗り降りするが駅のすぐ外は住宅地で、
新大久保は7万人だが駅前は商業地域である。
乗降客数で繁華街かどうかを判定すると、荻窪のほうが繁華街だという答えになる。

対処: 用途地域の容積率に置き換えた（`data/computed/zoning.json`）。
容積率は都市計画法にもとづいて定めた値で、地図を作った人の多さにも
乗り換え客の数にも左右されない。

### 3.3 施設の数は、人口密度を測っている

新大久保は駅から1,500m以内に小中学校が40校ある。等々力は21校である。
40校あるのは人口密度が高いからで、子育てに向くからではない。

対処: 学校・園・公園・スーパーは「歩ける範囲にいくつかあれば足りる」ものとして数え、
足りたぶんから先は加点しない（`saturate()`）。

### 3.4 半径を変えると、駅の順位が入れ替わる

800m圏で数えると、都心では隣の駅と圏が重なって差が消える。
淡路町と神田は800m圏のPOIの54%が同じもので、酒場の数は淡路町298軒・神田211軒と
実際とは逆に出ていた。300m圏で数え直すと淡路町41軒・神田83軒になった。

逆に300m圏だけで見ると、門前仲町と清澄白河のように、
店が駅から離れて広がる駅を取り落とす。

対処: 静かさは駅前の話なので300m圏だけで数える。
外食・カフェ・夜の店は、駅を出てすぐの多さ（300m）と
歩いて行ける選択肢の多さ（800m）を混ぜる。

### 3.5 重みを変えるだけでは、順位は直らない

渋谷は静かさが29点しかないが、通勤・乗換・買い物・医療がどれも95点を超える。
「夜は家で過ごす」を選んで静かさの重みを上げても、1軸の低さが他の軸の高さに埋もれる。

対処: 区分が重く見る軸に足切りをかけ、下位3割に入る駅を一覧の後ろへ回す
（`rankBySegment()`）。

### 3.6 家賃コスパは、絶対額の安さではない

池袋の `rentValue` は100である。ワンルーム8万9千円に対して通勤の利便性が
きわめて高いためで、コスパとしては正しい。
しかし家賃を抑えたい読み手が求めているのは絶対額の安さである。

対処: `rentLow`（絶対額の安さ）を別の軸として足した。

### 3.7 同じ名前の数字を、2つの定義で出していた

§2.5 のとおり。一覧と駅ページで総合評価が食い違っていた。

### 3.8 読み手が見つけた、文章そのものの失敗

測り方ではなく、書き方の失敗である。指摘を受けて直したものを、同じ順で残す。

| 何が起きていたか | どう直したか | ルール |
|---|---|---|
| 同じ駅名の2駅を区別せず「静かさは早稲田が上回る。ただし都心への近さは早稲田が上回る」と書いていた | 路線が多いほうを代表とし、もう一方に路線名を添えて「早稲田（都電荒川線）」と書く | — |
| 変数名を使い回し、「使える路線は新大橋通り（大通り）が2m先にあるの1本だけである」になっていた | 道路の音を入れる変数の名前を分けた | — |
| 「乗換の利便性は100点満点で32点である」と本文に書いていた | 削った。32点が高いのか低いのかが読み手に伝わらない | 37 |
| 「国土地理院の標高APIから、駅と半径400mの8方位、計9点を読み取った値である」を本文に書いていた | 節の下に出典としてリンクだけ置いた | 9 |
| 「一言でいうと」が本文をそのまま繰り返していた | 一言には結論だけを書き、道路名と距離は本文に任せた | — |
| 「明和病院が410mほどの距離にある」と書いていた | 「徒歩7分ほどの距離にあります」に直した。どこから測った値か読み手に伝わらない | 46 |
| 「ワンルームが12万〜13万円、1Kが…である」と主語なしで数字を並べていた | 「駅周辺の家賃相場は、ワンルームが…です」と、何の数字かを先に書く | 48 |
| 本文全体がである調だった | 読み手に見せる日本語はですます調に統一した | 47 |
| 「差を生む要因」と書いていた | 何の差かを書いて「家賃の差を生む要因」にした | 30 |

| 浸水の説明が事実の羅列で、ページの注記とも重なっていた | つなぎの言葉を入れ、締めの一文を置き、重なる2文を削った | 49 |
| 出典の名前が長かった | 「国交省ハザードマップ」のように短くした | 49 |
| 「家賃がこの水準である理由」の節に、相場の数字しか書いていなかった | 通勤時間に対する位置と、相場を押し上げる材料・抑える材料を書いた | 49 |
| 近くの駅との比較が、上回る点だけで終わっていた | 路線名・通勤時間の例・引き換えの軸まで書いた | 49 |
| 比較の「一言でいうと」が、本文を短くしただけだった | 「鉄道の便を取るなら住吉、治安を取るなら菊川です」に変えた | 49 |
| 1万円未満の差を「0.6万円」と書いていた | 「6千円」と書くようにした | 1 |
| 大崎→品川が「乗換1回・13分」と出ていた（実際は山手線で1駅） | 路線データが山手線を大崎始まり・品川終わりの列で持っており、環状がつながっていなかった。端どうしをつなぎ、数分の差なら乗り換えない経路を選ぶようにした | — |

| 「買い物のしやすさは大崎広小路のほうが上です」に根拠が無かった | 歩いて13分ほどの範囲のスーパーの数と、店の名前を添えた | 39 |
| 混雑率の一言が「とても高い」なのに、本文は「この駅はいちばん混む区間に入りません」だった | 一言も、いちばん混む区間に入るかどうかを先に見て決める | 39 |

## 4. やらないと決めたこと

| 決めたこと | 理由 |
|---|---|
| 物件一覧を機械で巡回して集めない | 各サイトの利用規約に反する。家賃相場は人が見て記録する（[08-data-sources-rent.md](./08-data-sources-rent.md) §E） |
| 在住者コメントを AI に書かせない | 構想 §4.2 の差別化の中核で、AI に書かせた時点でこのサービスの存在理由が消える |
| 独自ドメインが決まるまで検索エンジンに登録させない | 仮のアドレスが登録されると、移したあとも同じ内容のページが2つある状態になる |
| 連絡先のアドレスをソースに書かない | 公開したページのアドレスは収集され、迷惑メールが届く。環境変数で渡す |
| 浅い記事を13言語に翻訳しない | まず日本語で作り切る。深さでしか既存のまとめ記事に勝てない |
| 根拠のない金額や評価語で埋めない | §2.1、§2.7、§2.8 |
| 数を絶対値で頭打ちにしない | §2.2 |

## 5. いま分かっている弱いところ

直す順番を決めるために、分かっている限界を書いておく。

| 項目 | 状態 |
|---|---|
| `style` と `internationalFriendliness` | 未着手。18軸のうちこの2軸だけ空いている |
| 静かさの測り方 | 駅から300mで測っている。読み手が知りたいのは住む区画の静けさなので、500〜800mの帯に変えるかを検討中（[03-scoring.md](./03-scoring.md) §4.5） |
| ファミリー適性 | 治安を足して新大久保の誤りは直ったが、施設の数には人口密度がまだ残る |
| 家賃相場 | 443駅ぶん。残り15駅は未取得 |
| 在住者コメント | 33駅を「住んだ駅」と「調べた駅」に分ける作業が済んでいない |
| 深さ17層 | 全458駅のうち33駅だけが完成している |
| 鉄道の音 | 地上か高架か地下かのデータが無く、静かさに入っていない |

## 7. 作業の進め方

毎回この順で進める。

1. **読み手として出力を読む。**スコアの表ではなく、できあがった駅ページを読む
2. **誤りの種類を見つける。**1駅の誤りではなく、同じ原因で起きている誤りの集まりを探す
3. **全部直す。**1駅だけ直して終わりにしない
4. **ルールにする。**同じ失敗が次に出ないよう、文書に書く
5. **機械で検出できるようにする。**`check:ja` や `validate:data` に入れられるなら入れる
6. **確かめる。**`npm run validate:data` `npm run check:ja` `npm run typecheck` `npm run build` を通す

人が目で確かめるための道具もある。

```bash
npm run --silent review:segments > out.md   # 8区分の上位駅を点数つきで並べる
npm run check:coverage                      # 店の登録が、乗降客数から見て少ない駅
```
