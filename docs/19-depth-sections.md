# 19. データから組み立てた駅の「深さ」の節を書く

人が本文を書いた33駅には、次の5つの節がある。データから組み立てた425駅では、これが空欄になっていた。

| 節 | フィールド | 何を書くか |
|---|---|---|
| 朝・昼・夜・週末のようす | `faces.morning` `faces.daytime` `faces.night` `faces.weekend` | 時間帯ごとに、駅のまわりで何が起きるか |
| 夜道 | `nightWalk` | 夜に駅から家まで歩くときに、何を確かめればよいか |
| どんな人が住んでいるか | `residents` | 住んでいる人の顔ぶれ |
| 住まいの種類 | `housingStock` | どんな建物・部屋が多いか |
| これからの見通し | `outlook` | 再開発など、街がこれからどう変わるか |

既存の不動産まとめ記事に対する優位は「深さ」でしか作れない（CLAUDE.md）。
この5つの節が、データだけで組み立てた駅のページを薄くしている最大の理由である。
そこで、1日の過ごし方（[18-persona-days.md](./18-persona-days.md)）と同じ進め方で、
データと街の特色からエージェントが書き、読み直したものを `depthStatus: "reviewed"` として出す。

## 1. 使ってよい事実

**ここに挙げた出典にあることだけを書く。**あなたの知識で店名・施設名・数字・出来事を足さない（ルール35）。

| 出典 | 中身 | 主に使う節 |
|---|---|---|
| `data/content/ja/{slug}.json` の本文 | congestion（朝の混雑）、groceries、medical、noiseSources、hazards、terrain、rentRange、rentReason、stationNote | すべて |
| `data/town-traits/rehouse.json`・`data/town-traits/wikipedia.json` | 記事から読み取った街の特色 | すべて。`residents` と `outlook` はこれが無ければ書かない |
| `data/computed/pois.json` | 地図データ上の店・施設。`openingHours` に営業時間がある | `faces`・`nightWalk` |
| `data/computed/crime.json` | 駅のまわりの町丁の犯罪認知件数（警視庁） | `nightWalk` |
| `data/computed/zoning.json` | 半径500mの用途地域の割合（住居系・商業系・工業系など） | `housingStock`・`faces` |
| `data/computed/buildings.json` | 半径500mの商業・事務所の建物の階数の合計 | `housingStock`・`faces` |
| `data/computed/passengers.json` | 1日の乗降客数 | `faces` |
| `data/computed/roads.json` | 幹線道路・高速道路までの距離 | `faces`・`nightWalk` |
| `data/computed/scores.json` | 軸ごとの点（23区の駅どうしの相対的な位置） | 補助として |
| `data/computed/coverage-gaps.json` | 地図データの登録がまわりの駅より大きく少ない駅と種類 | ここに載っている種類の施設は「少ない」と書かない |

## 2. 節ごとの書き方

### faces（朝・昼・夜・週末）

4つとも、それぞれ2〜3文で書く。

- **morning**: 本文の `congestion` と同じ事実を使い、どちらへ向かう列車の話かを書く（ルール44）。
  乗降客数や、駅のまわりがオフィス街か住宅地か（zoning・buildings）から、改札を出る人の向きを書いてよい。
- **daytime**: 昼に開いている店（pois の飲食店・カフェの数、商店街の特色）、オフィスか住宅か。
- **night**: 酒場の数と、地図データで夜遅くまで営業している店。人の音と車の音を分けて書く（ルール41）。
- **weekend**: 街の特色にある祭り・行事・来街者、広い公園、商業施設。

### nightWalk（夜道）

- 犯罪の認知件数は、警視庁の統計の事実として書き、「危険」「安全」と評価しない。
- 夜遅くまで営業している店や酒場が帰り道に並ぶか、幹線道路沿いか住宅街の細い道かを書く。
- 街灯の明るさや人通りは、出典に書かれていなければ書かない。
  そのかわり「部屋を決める前に、夜に一度歩いて確かめておきたいところです」と、確かめる方法へ導く。

### residents（どんな人が住んでいるか）

- **街の特色の記事に、住んでいる人について書かれているときだけ書く。**無ければ、このフィールドを作らない。
- 学校・保育園の数や家賃の帯から、年齢層や世帯の構成を推して書かない。統計で確かめていないため。

### housingStock（住まいの種類）

- 用途地域の割合（低層住居専用地域が多い、商業地域が大半など）と、街の特色にある建物（団地、タワーマンション、木造の住宅密集地）を書く。
- 家賃の帯（ワンルームと2LDKの差など）から、どんな部屋が多そうかを書くときは「〜とみられます」と言い切らない。

### outlook（これからの見通し）

- **街の特色の記事に、再開発・建て替え・新しい施設の計画が書かれているときだけ書く。**無ければ作らない。
- 時期や規模は、記事に書かれた範囲で書く。完成した年がすでに過ぎていたら、そのことが分かる書き方にする。

## 3. 一言（leads）

5つの節には、それぞれ「一言でいうと」を付ける（`leads.faces`・`leads.nightWalk`・`leads.residents`・`leads.housingStock`・`leads.outlook`）。
節を作らなかったときは、その一言も作らない。1文、60字以内。

## 4. 守ること

- ですます調で書く。1文60字以内。比喩を使わない（CLAUDE.md の「とくに出やすい失敗」と「二つめに出やすい失敗」を見る）。
- 地図データ（pois.json）にしかない店・施設には「地図データ上の」と添える。
- 浸水は、何の浸水かを省かずに書く（ルール45）。駅から施設までの距離はメートルで書かない。
- 同じ述語を3回以上続けない。
- 書き終えたら `depthStatus` を `"reviewed"` にする。ほかのフィールドは触らない。
- `npm run check:ja` と `npm run validate:data` を通す。

## 5. 組み立て直しとの関係

`scripts/build-station-content.py` は、データから組み立てた駅の本文を作り直すときに、
この5つの節と、その一言と、`depthStatus` を消さずに残す。
本文のデータ（混雑率・店・家賃など）が変わったときは、この節の記述と食い違っていないかを確かめ直す。
