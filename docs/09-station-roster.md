# 掲載候補の全駅（ロースター）

「まず対象になる駅を全部洗い出す」ためのデータ。駅名・所在区・路線までを持ち、
家賃やスコアは含まない。詳細プロフィール（`data/stations/`）はこの一覧から順に作る。

生成日: 2026-09-06 / 再生成: `python3 scripts/build-roster.py`

---

## 1. 対象範囲

| 区分 | 対象 |
|---|---|
| 都営 | 浅草線・三田線・新宿線・大江戸線・都電荒川線・日暮里舎人ライナー |
| 東京メトロ | 銀座・丸ノ内・日比谷・東西・千代田・有楽町・半蔵門・南北・副都心 |
| JR | 山手線・中央線(快速)・中央総武線 |
| 私鉄等 | 東武（東上・伊勢崎・亀戸・大師）、西武（池袋・有楽町・豊島・新宿）、京成（本線・押上・金町）、京王（京王線・井の頭・新線）、小田急、東急（東横・目黒・田園都市・大井町・池上・多摩川・世田谷）、京急（本線・空港）、つくばエクスプレス、ゆりかもめ、東京モノレール、りんかい線、北総線、埼玉高速 |

そのうえで **23区内の駅のみ** を残す。

**結果: 443駅 / 62路線 / 23区すべて**

対象路線に含まれる駅は765件で、うち322件は23区外（東急の神奈川県内、京王・小田急・西武の多摩地区、東武東上線の埼玉県内、つくばEXの千葉・茨城など）として除外した。

### 路線の扱いについて

対象路線は「**どの駅を載せるか**」の定義であり、「どの路線を表示するか」ではない。
各駅には、対象外の路線も含めて**その駅を通る全路線**を持たせている。
たとえば大井町は京浜東北線が対象路線に入っていないが、駅としては対象なので
京浜東北線も路線一覧に出る。

## 3. 所在区をどう判定したか

駅の座標から所在区を求める。二つの方法を試して、後者を採った。

### 採らなかった方法: 区の境界ポリゴン

入手できる簡略化された境界データでは、**江東区が埋立地の一部しか含まず、江戸川区は細い断片だけ**になっていた。これで判定すると江東区が4駅、江戸川区が0駅という明らかにおかしい結果になる。

### 採った方法: 町丁の代表点の最近傍

首都圏（東京・埼玉・千葉・神奈川）の町丁 21,449 点から最も近い点を探し、その市区町村を所在区とする。隣接する市部の点も候補に入れているので、23区外の駅を誤って区に含めることがない。

### 判定できない駅の扱い

区境に建つ駅は、この方法では決まらない。座標の数十メートルの差で結果が変わる。
該当する駅は `WARD_OVERRIDE` に駅の所在地表記を書いて上書きしている。

現在の上書き対象: 目黒（品川区）、御茶ノ水・水道橋・市ケ谷・飯田橋（千代田区）、自由が丘（目黒区）、新大塚（文京区）。

> **既知の限界**: 区境の駅は、まだ気づいていない誤りが残っている可能性がある。
> 気づいたら `WARD_OVERRIDE` に足して再生成する。43駅の抜き取り検算はすべて一致している。

## 4. 生成時に踏んだ落とし穴

同じ問題を繰り返さないための記録。

1. **同じ駅でも路線ごとに座標が違う。**
   どの路線ファイルを先に読むかで区の判定が変わり、実行するたびに結果が揺れた。
   全路線の座標の平均を代表点にして解決。

2. **ekidata は連絡駅を1つの駅グループにまとめている。**
   有楽町と日比谷、王子と王子駅前、三越前と新日本橋、成増と地下鉄成増が同一グループ。
   「どの街に住むか」を決める用途では同じ場所として扱ってよいが、
   駅名を路線ファイルから拾うと表示名とローマ字が別の駅のものになる
   （三越前に Shin-Nihombashi が付くなど）。
   駅名は全国データ側の代表名を使い、ローマ字は**駅名が一致するもの**から引くようにした。

3. **上書き設定が表記ゆれで黙って効かない。**
   `市ケ谷`（小さいケ）と `市ヶ谷`（大きいヶ）で上書きが一度も適用されず、
   誤った区のまま出ていた。
   いまは**一度も使われなかった上書きキーがあるとビルドを失敗させる**。

4. **新しい駅は全国データのスナップショットに載っていない。**
   高輪ゲートウェイが路線情報ゼロで出てきた。
   対象路線からの所属と全国データを合わせて解決。

## 5. データ構造

`data/roster/stations.json`

```jsonc
{
  "slug": "kiyosumi-shirakawa",
  "nameJa": "清澄白河",
  "nameRomaji": "Kiyosumi-Shirakawa",
  "ward": "koto",
  "wardCode": "13108",
  "wardNameJa": "江東区",
  "lat": 35.681067,
  "lon": 139.800829,
  "lineIds": ["28008", "99301"]
}
```

`data/reference/lines.json`

```jsonc
{ "id": "99301", "nameJa": "都営大江戸線", "nameEn": "Toei Oedo Line", "operator": "toei" }
```

駅プロフィール（`data/stations/`）も路線は `lineIds` で参照する。443駅規模で路線名を各駅に書くと二重管理になるため。

`npm run validate:data` が以下を検証する。

- ロースターの slug が一意であること
- すべての `lineIds` が路線マスタに存在すること
- 詳細プロフィールがロースターの部分集合であること
- 詳細プロフィールの駅名・所在区がロースターと一致すること

## 6. これは何ではないか

ロースターは**駅の存在と所在の一覧**であって、住みやすさの評価ではない。

- 家賃・通勤時間・スコア・在住者コメントは含まない
- ロースターにあることは「掲載予定」を意味するだけで、駅ページがあることを意味しない
- サイト上では `/{locale}/roster` で一覧でき、詳細プロフィールがある駅だけリンクになる

443駅すべてに詳細プロフィールを作るかどうかは、まだ決めていない（[06-roadmap.md](./06-roadmap.md) の論点）。
